# WorkManager design specification

## 核心功能原則

WM（WorkManager，工作管理者）為平行處理架構中之協調服務單元，須包含以下核心機制，作為系統設計之非協商準則。

### I. Inter-process communication（工作訊息接收機制）

+ WM 須提供工作訊息接收機制，基於程序間通訊（IPC）接收外部工作訊息。
+ 通訊機制之選型須考量 Socket 通訊與 Pipe 通訊兩種方案。

**Rationale**: 工作訊息接收機制為 WM 定義中明列之核心機制；Socket 通訊與 Pipe 通訊為文件明列之考量方案，故均屬通訊機制選型之非協商考量範圍。

**EXAMPLE**:
```python
# app/wm/core/message_receiver.py
import abc
import socket


class MessageReceiver(abc.ABC):
    @abc.abstractmethod
    def receive(self) -> bytes:
        raise NotImplementedError


class SocketMessageReceiver(MessageReceiver):
    def __init__(self, host: str, port: int) -> None:
        self._server = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        self._server.bind((host, port))
        self._server.listen()

    def receive(self) -> bytes:
        conn, _ = self._server.accept()
        with conn:
            return conn.recv(4096)


class PipeMessageReceiver(MessageReceiver):
    def __init__(self, pipe_path: str) -> None:
        self._pipe_path = pipe_path

    def receive(self) -> bytes:
        with open(self._pipe_path, "rb") as pipe:
            return pipe.read()
```

### II. Message queue（工作訊息佇列機制）

+ WM 須將基於 IPC 取得之工作訊息，佇列至資訊儲存區。
+ 資訊儲存區須以工作清單（JSON 格式）呈現，並包括執行時間記錄、執行狀態記錄、執行內容。
+ 工作清單須儲存於 `/tmp` 目錄中，供工作者（Worker）或通訊監反饋使用。

**Rationale**: 工作訊息佇列機制為 WM 定義中明列之核心機制；JSON 格式、`/tmp` 儲存位置，以及執行時間、執行狀態、執行內容三項記錄內容，均為文件明列之儲存規範，故屬非協商要求。

**EXAMPLE**:
```python
# app/wm/core/message_queue.py
import json
import time
import uuid
from pathlib import Path

WORK_LIST_DIR = Path("/tmp/wm_worklist")


def enqueue_work_message(content: dict) -> str:
    work_id = str(uuid.uuid4())
    record = {
        "work_id": work_id,
        "status": "pending",
        "content": content,
        "execution_time": {"created": time.time(), "updated": None},
    }
    WORK_LIST_DIR.mkdir(parents=True, exist_ok=True)
    (WORK_LIST_DIR / f"{work_id}.json").write_text(json.dumps(record))
    return work_id


def read_work_record(work_id: str) -> dict:
    return json.loads((WORK_LIST_DIR / f"{work_id}.json").read_text())


def update_work_status(work_id: str, status: str) -> None:
    record = read_work_record(work_id)
    record["status"] = status
    record["execution_time"]["updated"] = time.time()
    (WORK_LIST_DIR / f"{work_id}.json").write_text(json.dumps(record))
```

### III. Workers coordination（工作指派機制）

+ 每份工作清單須指派給一個空閒的工作者（Worker）執行。
+ Worker 完成工作後，須修改對應工作清單之狀態，並記錄執行時間。
+ Worker 執行之內容須依據工作清單之執行內容決定；其運作方式為依內容調用對應工作模組，將內容傳遞予模組，並等待模組完成。

**Rationale**: 工作指派機制為 WM 定義中明列之核心機制；空閒指派、完成後狀態與時間更新、依內容調用工作模組等運作方式，均為文件明列之流程，故屬非協商要求。

**EXAMPLE**:
```python
# app/wm/core/coordinator.py
import importlib

from app.wm.core.worker_pool import WorkerPool
from app.wm.core.message_queue import read_work_record, update_work_status


def dispatch_work(worker_pool: WorkerPool, work_id: str) -> None:
    worker = worker_pool.select_idle_worker()
    worker.execute(work_id)


def load_work_module(module_name: str):
    return importlib.import_module(f"app.modules.{module_name}")


class Worker:
    def execute(self, work_id: str) -> None:
        record = read_work_record(work_id)
        update_work_status(work_id, status="running")
        module = load_work_module(record["content"]["module"])
        module.run(record["content"])
        update_work_status(work_id, status="completed")
```

### IV. Workers management（工作者數量管理機制）

+ Worker 數量須受限制，限制機制須至少考量下列面向：
  - 記憶體使用量：依據單一 Worker 之記憶體用量估計值，配合可用記憶體上限，計算 Worker 數量上限。
  - 處理效率量（CPU）：當現有 Worker 皆在執行工作，且整體 CPU 使用率仍未達限制值時，得建立新 Worker。
+ 上述為文件明列之常見規劃方向；以下為依此方向之設計參考：
  - Worker 數量上限（記憶體面向）＝可用記憶體 ÷ 單一 Worker 預估記憶體用量。
  - 新增 Worker 之條件（CPU 面向）＝現有 Worker 皆忙碌，且 CPU 使用率 < 限制值。
  - 兩項限制須同時滿足：新增 Worker 前，須確認未超出記憶體面向之數量上限。

**Rationale**: 工作者數量管理機制為 WM 定義中明列之核心機制；記憶體使用量與處理效率量（CPU）為文件明列之常見規劃方向，故屬非協商考量範圍。其餘具體門檻計算與合併判斷邏輯，係依文件所述「請詳列相關設計規範作為設計參考」之指示，基於前述兩項方向所作之設計參考。

**EXAMPLE**:
```python
# app/wm/core/worker_pool.py
class WorkerPool:
    def __init__(
        self,
        per_worker_memory_mb: int,
        available_memory_mb: int,
        cpu_limit_percent: float,
    ) -> None:
        self._workers: list["Worker"] = []
        self._max_workers_by_memory = available_memory_mb // per_worker_memory_mb
        self._cpu_limit_percent = cpu_limit_percent

    def count(self) -> int:
        return len(self._workers)

    def select_idle_worker(self) -> "Worker":
        return next(worker for worker in self._workers if not worker.is_busy())

    def can_scale_up(self, current_cpu_percent: float) -> bool:
        if self.count() >= self._max_workers_by_memory:
            return False
        all_busy = all(worker.is_busy() for worker in self._workers)
        return all_busy and current_cpu_percent < self._cpu_limit_percent

    def register(self, worker: "Worker") -> None:
        self._workers.append(worker)

    def unregister(self, worker: "Worker") -> None:
        self._workers.remove(worker)
```

## 技術與架構規範

WM 專案之技術選型與專案結構如下，作為實作時之非協商準則。

### V. Python 程式語言規範

+ WM 專案須以 Python 作為實作語言。

**Rationale**: Python 為服務項目中明定之程式語言，故為非協商要求。

**EXAMPLE**:
```python
# app/wm/main.py
def main() -> None:
    start_message_receiver(host="0.0.0.0", port=9000)


if __name__ == "__main__":
    main()
```

### VI. 專案結構規範

+ `app/wm` 為工作管理者專案根目錄，其下須包含：
  - `conf`：配置資訊目錄。
  - `core`：共通服務目錄。
  - `main.py`：工作管理者專案進入點。
+ `app/modules` 為工作模組目錄。

**Rationale**: 專案結構為專案結構項目中明定之目錄配置，故為非協商要求。

**EXAMPLE**:
```python
# app/wm/main.py
from app.wm.core import coordinator
from app.wm.conf import settings


def main() -> None:
    coordinator.run(settings.load())


if __name__ == "__main__":
    main()
```
