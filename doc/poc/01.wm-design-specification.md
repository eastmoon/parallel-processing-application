## 核心功能原則

WM（WorkManager，工作管理者）為平行處理架構中之協調服務單元，須包含以下核心機制，作為系統設計之非協商準則。各原則之範例程式共同構成一組相互引用之模組，檔案配置見原則 VI。

### I. Inter-process communication（工作訊息接收機制）

+ WM 須提供工作訊息接收機制，基於程序間通訊（IPC）接收外部工作訊息。
+ 通訊機制之選型須考量 Socket 通訊與 Pipe 通訊兩種方案，並以共同之接收介面封裝，使訊息佇列機制（原則 II）不依賴特定通訊方案。
+ 串流型通訊不保留訊息邊界，須訂定訊息框架；本規格採用 JSON Lines，即每則訊息為一行 UTF-8 編碼之 JSON 物件，以 `\n` 結尾。
+ Socket 通訊考量項目：
  - 位址族：同一主機內之通訊使用 Unix domain socket（`AF_UNIX`，以檔案路徑定址）；跨主機通訊使用 TCP（`AF_INET`）。
  - 連線模式：伺服端以 `listen()`、`accept()` 接受連線，可服務多個訊息來源；來源關閉連線即表示該連線之訊息傳送結束。
  - 殘留檔案：`AF_UNIX` 綁定之路徑於程序結束後仍存在，啟動時須先移除再綁定。
+ Pipe 通訊考量項目：
  - 匿名管道（`os.pipe`、`multiprocessing.Pipe`）僅適用於具親緣關係之程序，由父程序建立後由子程序繼承。
  - 具名管道（FIFO，`os.mkfifo`）以檔案路徑定址，可供無親緣關係之程序使用，僅適用於 POSIX 系統。
  - 以阻塞模式開啟 FIFO 時，讀取端與寫入端須雙方皆已開啟才返回；所有寫入端關閉後，讀取端讀到 EOF，須重新開啟以持續接收。
  - 多個寫入端同時寫入時，單次寫入量不超過 `PIPE_BUF`（POSIX 規定至少 512 bytes，Linux 為 4096 bytes）方保證不互相交錯；訊息長度可能超過此值時，須改用 Socket 通訊。

**Rationale**: 工作訊息接收機制為 WM 定義中明列之核心機制，Socket 與 Pipe 為明列之考量方案。兩者於定址方式、程序關係與訊息邊界之特性不同，故以共同介面與固定訊息框架隔離差異。

> 驗證方式：邏輯檢查｜目標環境：Python 3.10 以上、Linux

```python
# app/wm/core/receiver.py
import json
import os
import socket
from abc import ABC, abstractmethod
from collections.abc import Iterator


def _decode_lines(stream) -> Iterator[dict]:
    """逐行解碼 JSON Lines；空行、格式錯誤或非 JSON 物件之行略過。"""
    for line in stream:
        try:
            message = json.loads(line)
        except json.JSONDecodeError:
            continue
        if isinstance(message, dict):
            yield message


class MessageReceiver(ABC):
    """工作訊息接收介面；訊息框架為 JSON Lines（每行一則 JSON 物件）。"""

    @abstractmethod
    def messages(self) -> Iterator[dict]:
        raise NotImplementedError


class UnixSocketReceiver(MessageReceiver):
    def __init__(self, path: str) -> None:
        if os.path.exists(path):
            os.unlink(path)  # 移除前次執行殘留之 socket 檔案
        self._server = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        self._server.bind(path)
        self._server.listen()

    def messages(self) -> Iterator[dict]:
        while True:  # 依序處理連線；需並行處理多個連線時可搭配 selectors 或執行緒
            conn, _ = self._server.accept()
            with conn, conn.makefile("r", encoding="utf-8", errors="replace") as stream:
                yield from _decode_lines(stream)  # 來源關閉連線時結束


class FifoReceiver(MessageReceiver):
    def __init__(self, path: str) -> None:
        if not os.path.exists(path):
            os.mkfifo(path)
        self._path = path

    def messages(self) -> Iterator[dict]:
        while True:
            # 所有寫入端關閉後讀到 EOF，離開 with 區塊後重新開啟以持續接收
            with open(self._path, encoding="utf-8", errors="replace") as stream:
                yield from _decode_lines(stream)


def send_by_socket(path: str, message: dict) -> None:
    """訊息來源端：以 Unix domain socket 送出一則訊息。"""
    with socket.socket(socket.AF_UNIX, socket.SOCK_STREAM) as client:
        client.connect(path)
        client.sendall((json.dumps(message) + "\n").encode("utf-8"))


def send_by_fifo(path: str, message: dict) -> None:
    """訊息來源端：以單次 write 送出一則訊息，長度不超過 PIPE_BUF 時不與其他寫入端交錯。"""
    data = (json.dumps(message) + "\n").encode("utf-8")
    if len(data) > os.pathconf(path, "PC_PIPE_BUF"):
        raise ValueError("message exceeds PIPE_BUF; use send_by_socket")
    fd = os.open(path, os.O_WRONLY)  # 阻塞至讀取端開啟
    try:
        os.write(fd, data)
    finally:
        os.close(fd)
```

### II. Message queue（工作訊息佇列機制）

+ WM 須將基於 IPC 取得之工作訊息，佇列至資訊儲存區。
+ 資訊儲存區須以工作清單（JSON 格式）呈現，並包括執行時間記錄、執行狀態記錄、執行內容。
+ 工作清單須儲存於 `/tmp` 目錄中，供工作者（Worker）或通訊監反饋使用。
+ 設計參考：
  - 儲存單位：每份工作清單為一個 JSON 檔案，路徑為 `/tmp/wm/worklist/<id>.json`，使指派（原則 III）以單一檔案為單位進行。
  - 欄位定義：
    - `id`：工作識別碼（UUID）。
    - `status`：執行狀態記錄，依序為 `pending`（已佇列）→ `assigned`（已指派）→ `running`（執行中）→ `completed`（完成）或 `failed`（失敗）。
    - `content`：執行內容，須為 JSON 物件並包含欲調用之工作模組名稱 `module`，其餘欄位為傳遞予模組之參數。
    - `time`：執行時間記錄，包含 `created`（佇列時間）、`started`（開始執行時間）、`finished`（結束時間），以 epoch 秒表示，未發生者為 `null`。
  - 取出順序：待指派之工作依 `time.created` 先進先出（FIFO）。
  - 寫入一致性：WM 與 Worker 分屬不同程序，寫入時須先寫入同目錄之暫存檔，再以 `os.replace` 替換；同一檔案系統內之替換為原子操作，讀取端不會讀到寫入中之內容。
  - 單一寫入者：工作清單於 `assigned` 前僅由 WM 寫入，之後僅由受指派之 Worker 寫入，避免多個寫入者同時更新同一檔案。
  - 揮發性：`/tmp` 可能為 tmpfs 或於開機時清除，工作清單不保證跨重新開機保存。

工作清單格式：

```json
{
  "id": "4f7c2d0e9b8a4c1f8e6d5a3b2c1d0e9f",
  "status": "pending",
  "content": {"module": "sample", "seconds": 2},
  "time": {"created": 1790000000.0, "started": null, "finished": null}
}
```

**Rationale**: 工作訊息佇列機制為 WM 定義中明列之核心機制；JSON 格式、`/tmp` 儲存位置，以及執行時間、執行狀態、執行內容三項記錄，均為明列之儲存規範。以檔案作為程序間共享之資訊儲存區時，讀寫交錯可能產生不完整之 JSON，故以原子替換與單一寫入者規範維持一致性。

> 驗證方式：邏輯檢查｜目標環境：Python 3.10 以上、Linux

```python
# app/wm/core/worklist.py
import json
import os
import tempfile
import time
import uuid
from pathlib import Path

WORKLIST_DIR = Path("/tmp/wm/worklist")


def _path(work_id: str) -> Path:
    return WORKLIST_DIR / f"{work_id}.json"


def _write_atomic(path: Path, record: dict) -> None:
    """寫入同目錄暫存檔後以 os.replace 替換，讀取端僅會讀到完整內容。"""
    fd, tmp = tempfile.mkstemp(dir=path.parent, suffix=".tmp")
    with os.fdopen(fd, "w", encoding="utf-8") as stream:
        json.dump(record, stream, ensure_ascii=False)
    os.replace(tmp, path)


def enqueue(content: dict) -> str:
    """將 IPC 取得之訊息佇列為一份工作清單，回傳工作識別碼。"""
    WORKLIST_DIR.mkdir(parents=True, exist_ok=True)
    work_id = uuid.uuid4().hex
    record = {
        "id": work_id,
        "status": "pending",
        "content": content,
        "time": {"created": time.time(), "started": None, "finished": None},
    }
    _write_atomic(_path(work_id), record)
    return work_id


def load(work_id: str) -> dict:
    return json.loads(_path(work_id).read_text(encoding="utf-8"))


def set_status(work_id: str, status: str) -> None:
    """更新執行狀態記錄，並於開始與結束時記錄執行時間。"""
    record = load(work_id)
    record["status"] = status
    if status == "running":
        record["time"]["started"] = time.time()
    elif status in ("completed", "failed"):
        record["time"]["finished"] = time.time()
    _write_atomic(_path(work_id), record)


def pending_ids() -> list[str]:
    """依 time.created 先進先出，列出待指派之工作識別碼。"""
    records = [json.loads(p.read_text(encoding="utf-8")) for p in WORKLIST_DIR.glob("*.json")]
    pending = [r for r in records if r["status"] == "pending"]
    return [r["id"] for r in sorted(pending, key=lambda r: r["time"]["created"])]
```

### III. Workers coordination（工作指派機制）

+ 每份工作清單須指派給一個空閒的工作者（Worker）執行。
+ Worker 完成工作後，須修改對應工作清單之狀態，並記錄執行時間。
+ Worker 執行之內容須依據工作清單之執行內容決定；其運作方式為依內容調用對應工作模組（`app/modules`），將內容傳遞予模組，並等待模組完成。
+ 設計參考：
  - 程序模型：Worker 以獨立程序實作。CPython 預設建置具全域直譯器鎖（GIL），同一程序內之執行緒無法平行執行 Python 位元組碼，故 CPU 密集之工作模組以多程序平行執行。
  - 指派通道：每個 Worker 具專屬之任務佇列（`multiprocessing.Queue`）；WM 僅傳送工作識別碼，Worker 自 `/tmp` 工作清單讀取執行內容。
  - 空閒判定：Worker 完成工作後，經由共用之回報佇列回報其識別碼；WM 據此維護空閒 Worker 集合，僅對空閒 Worker 指派，且一次指派一份工作清單。
  - 模組介面：工作模組為 `app.modules` 套件下之模組，提供 `run(content: dict)` 函式；Worker 以同步呼叫等待模組完成，函式返回即視為完成。
  - 模組名稱驗證：`content.module` 僅允許小寫英文字母、數字與底線，並限定於 `app.modules` 套件內載入，避免以訊息內容載入任意模組。
  - 失敗處理：模組拋出例外、模組不存在或執行內容格式錯誤時，狀態記為 `failed` 並記錄結束時間，Worker 回到空閒狀態。
  - 啟動方式：WM 含訊息接收執行緒，於多執行緒程序中以 `fork` 建立子程序可能複製已被其他執行緒持有之鎖而造成死結，故 Worker 以 `spawn` 啟動方式建立。

**Rationale**: 工作指派機制為 WM 定義中明列之核心機制；空閒指派、完成後狀態與時間更新、依內容調用工作模組並等待完成，均為明列之流程。以工作識別碼作為指派單位，使工作清單維持為執行內容之唯一來源。

**EXAMPLE**:
> 驗證方式：邏輯檢查｜目標環境：Python 3.10 以上、Linux

```python
# app/wm/core/worker.py
import importlib
import re
from multiprocessing.queues import Queue

from app.wm.core import worklist

_MODULE_NAME = re.compile(r"[a-z_][a-z0-9_]*")


def load_module(name: str):
    """僅允許載入 app.modules 套件下之工作模組。"""
    if not isinstance(name, str) or not _MODULE_NAME.fullmatch(name):
        raise ValueError(f"invalid module name: {name!r}")
    return importlib.import_module(f"app.modules.{name}")


def worker_loop(worker_id: int, tasks: Queue, reports: Queue) -> None:
    """Worker 程序：取得工作 → 調用工作模組並等待完成 → 更新工作清單 → 回報空閒。"""
    while (work_id := tasks.get()) is not None:  # None 為結束訊號
        try:
            content = worklist.load(work_id)["content"]
            worklist.set_status(work_id, "running")
            load_module(content["module"]).run(content)  # 同步呼叫，返回即視為完成
            worklist.set_status(work_id, "completed")
        except Exception:
            worklist.set_status(work_id, "failed")
        finally:
            reports.put(worker_id)
```

```python
# app/wm/core/coordinator.py
from app.wm.core import worklist
from app.wm.core.pool import WorkerPool


def dispatch(pool: WorkerPool) -> None:
    """依佇列順序將待執行工作指派給空閒 Worker，一份工作清單僅指派給一個 Worker。"""
    for work_id in worklist.pending_ids():
        worker_id = pool.acquire_idle()
        if worker_id is None:
            return  # 無空閒 Worker，其餘工作維持 pending
        worklist.set_status(work_id, "assigned")
        pool.send(worker_id, work_id)
```

### IV. Workers management（工作者數量管理機制）

+ Worker 數量須受限制，限制機制須至少考量下列面向：
  - 記憶體使用量：依據單一 Worker 之記憶體用量估計值與最大可用量，計算 Worker 數量上限。
  - 處理效率量（CPU）：當現有 Worker 皆在執行工作，且 CPU 使用率仍未達限制值時，建立新 Worker 執行工作。
+ 上述為常見規劃，其設計參考詳列如下。

#### 設計參考：配置參數

限制機制之參數集中於 `app/wm/conf`：

| 參數 | 說明 |
| --- | --- |
| `MIN_WORKERS` | 常駐 Worker 數量下限，WM 啟動時建立 |
| `MAX_WORKERS` | Worker 數量硬性上限；CPU 密集工作常以 `os.cpu_count()` 為預設值 |
| `PER_WORKER_MEMORY_MB` | 單一 Worker 記憶體用量估計值 |
| `MEMORY_BUDGET_MB` | 最大可用量之配置上限 |
| `MEMORY_RESERVE_MB` | 保留予 WM 本身與作業系統之記憶體量 |
| `CPU_LIMIT_PERCENT` | CPU 使用率限制值 |
| `SCALE_COOLDOWN_SEC` | 兩次新增 Worker 之最短間隔 |
| `EVALUATE_INTERVAL_SEC` | 指派與數量評估之週期，亦為 CPU 使用率之取樣區間 |
| `IDLE_TIMEOUT_SEC` | Worker 空閒超過此時間且數量大於下限時予以回收 |

#### 設計參考：記憶體使用量面向

+ 數量上限：`記憶體上限 = ⌊(最大可用量 − 保留量) ÷ 單一 Worker 記憶體用量⌋`，結果小於 0 時以 0 計。
+ 最大可用量：取 `MEMORY_BUDGET_MB` 與系統可用記憶體之較小值；Linux 3.14 以上可讀取 `/proc/meminfo` 之 `MemAvailable`，或使用第三方套件 `psutil.virtual_memory().available`。
+ 單一 Worker 記憶體用量估計：以工作模組實際執行之常駐記憶體（RSS）峰值為依據並保留餘裕；Worker 內可由 `resource.getrusage(resource.RUSAGE_SELF).ru_maxrss` 取得峰值（Linux 單位為 KiB）。
+ 動態確認：新增 Worker 前可再次讀取系統可用記憶體，確認扣除保留量後仍不小於單一 Worker 記憶體用量，以涵蓋其他程序占用記憶體之情形。
+ 優先順序：記憶體總用量超出可用記憶體時，系統可能使用交換空間（swap）或由 Linux OOM killer 終止程序，故記憶體上限優先於 CPU 面向之新增條件。

#### 設計參考：處理效率量（CPU）面向

+ 新增條件（須同時成立）：
  - 有待指派之工作（`pending` 數量大於 0）。
  - 無空閒 Worker（現有 Worker 皆在執行工作）。
  - CPU 使用率小於 `CPU_LIMIT_PERCENT`。
  - Worker 數量小於有效上限 `min(MAX_WORKERS, 記憶體上限)`。
  - 距上次新增 Worker 已達 `SCALE_COOLDOWN_SEC`。
+ CPU 使用率量測：以兩次取樣間之累計 CPU 時間差值計算。Linux 讀取 `/proc/stat` 第一行之 `user`、`nice`、`system`、`idle`、`iowait`、`irq`、`softirq`、`steal` 欄位，使用率為 `1 − (idle + iowait) 差值 ÷ 總差值`；或使用第三方套件 `psutil.cpu_percent()`。
+ 單步新增與冷卻時間：每次評估至多新增一個 Worker，冷卻時間內不再新增，使新 Worker 之負載反映於後續 CPU 取樣後再行判斷，避免連續新增超出實際需求。

#### 設計參考：數量回收

+ 空閒回收：Worker 空閒超過 `IDLE_TIMEOUT_SEC` 且數量大於 `MIN_WORKERS` 時，送出結束訊號回收該 Worker；指派時優先使用最近轉為空閒之 Worker，使其餘空閒 Worker 得以逾時回收。
+ 異常回收：Worker 程序異常結束（`Process.is_alive()` 為假）時，自數量計算中移除，WM 依指派紀錄將其未完成之工作清單標記為 `failed`；數量低於 `MIN_WORKERS` 時重新建立。

**Rationale**: 工作者數量管理機制為 WM 定義中明列之核心機制；記憶體使用量與處理效率量（CPU）為明列之常見規劃方向。記憶體面向決定數量之硬性上限，CPU 面向決定上限內是否提高並行度；配置參數、冷卻時間與回收規則係依描述「請詳列相關設計規範作為設計參考」列出之設計參考。

**EXAMPLE**:
> 驗證方式：邏輯檢查｜目標環境：Python 3.10 以上、Linux

```python
# app/wm/core/pool.py
import multiprocessing
import queue
import time
from multiprocessing.process import BaseProcess
from multiprocessing.queues import Queue

from app.wm.core.worker import worker_loop

_CTX = multiprocessing.get_context("spawn")  # WM 含接收執行緒，不以 fork 建立 Worker


def mem_available_mb() -> int:
    """Linux：讀取 /proc/meminfo 之 MemAvailable（kB）並換算為 MB。"""
    with open("/proc/meminfo", encoding="ascii") as stream:
        for line in stream:
            if line.startswith("MemAvailable:"):
                return int(line.split()[1]) // 1024
    raise RuntimeError("MemAvailable not found in /proc/meminfo")


def max_workers_by_memory(budget_mb: int, reserve_mb: int, per_worker_mb: int) -> int:
    """記憶體上限 = ⌊(最大可用量 − 保留量) ÷ 單一 Worker 記憶體用量⌋。"""
    return max((budget_mb - reserve_mb) // per_worker_mb, 0)


class CpuSampler:
    """以兩次取樣間 /proc/stat 累計 CPU 時間之差值計算整體 CPU 使用率（%）。"""

    def __init__(self) -> None:
        self._last = self._read()

    @staticmethod
    def _read() -> tuple[int, int]:
        with open("/proc/stat", encoding="ascii") as stream:
            fields = [int(v) for v in stream.readline().split()[1:9]]  # user … steal
        return fields[3] + fields[4], sum(fields)  # (idle + iowait, total)

    def percent(self) -> float:
        idle, total = self._read()
        last_idle, last_total = self._last
        self._last = (idle, total)
        delta = total - last_total
        return 100.0 * (delta - (idle - last_idle)) / delta if delta > 0 else 0.0


def should_scale_up(*, pending: int, idle: int, count: int, limit: int,
                    cpu: float, cpu_limit: float, since_last: float, cooldown: float) -> bool:
    """CPU 面向之新增條件；limit 為 min(MAX_WORKERS, 記憶體上限)。"""
    return (
        pending > 0
        and idle == 0
        and count < limit
        and cpu < cpu_limit
        and since_last >= cooldown
    )


class WorkerPool:
    def __init__(self) -> None:
        self._reports: Queue = _CTX.Queue()
        self._tasks: dict[int, Queue] = {}
        self._procs: dict[int, BaseProcess] = {}
        self._idle: dict[int, float] = {}  # worker_id → 轉為空閒之時間
        self._next_id = 0
        self.last_spawn = float("-inf")

    @property
    def count(self) -> int:
        return len(self._procs)

    @property
    def idle_count(self) -> int:
        return len(self._idle)

    def spawn(self) -> None:
        worker_id, self._next_id = self._next_id, self._next_id + 1
        tasks = _CTX.Queue()
        proc = _CTX.Process(target=worker_loop, args=(worker_id, tasks, self._reports))
        proc.start()
        self._tasks[worker_id], self._procs[worker_id] = tasks, proc
        self._idle[worker_id] = self.last_spawn = time.monotonic()

    def collect_reports(self) -> None:
        """接收 Worker 完成回報，將其標記為空閒。"""
        while True:
            try:
                self._idle[self._reports.get_nowait()] = time.monotonic()
            except queue.Empty:
                return

    def acquire_idle(self) -> int | None:
        """取出最近轉為空閒之 Worker。"""
        if not self._idle:
            return None
        worker_id = next(reversed(self._idle))
        del self._idle[worker_id]
        return worker_id

    def send(self, worker_id: int, work_id: str) -> None:
        self._tasks[worker_id].put(work_id)

    def retire_idle(self, timeout: float, minimum: int) -> None:
        """回收空閒逾時之 Worker，數量不低於下限。"""
        now = time.monotonic()
        for worker_id, since in list(self._idle.items()):
            if self.count <= minimum:
                return
            if now - since >= timeout:
                del self._idle[worker_id]
                tasks = self._tasks.pop(worker_id)
                tasks.put(None)  # 空閒 Worker 取得結束訊號後離開主迴圈
                self._procs.pop(worker_id).join()

    def shutdown(self) -> None:
        for tasks in self._tasks.values():
            tasks.put(None)
        for proc in self._procs.values():
            proc.join()
```

## 技術與架構規範

WM 專案之技術選型與專案結構如下，作為實作時之非協商準則。

### V. Python 程式語言規範

+ WM 專案須以 Python 作為實作語言，版本為 Python 3.10 以上；範例使用之 `int | None` 型別語法於執行期須 3.10 以上版本。
+ 執行環境為 Linux：`/tmp` 為明列之儲存位置，且 FIFO（`os.mkfifo`）、Unix domain socket（`AF_UNIX`）與 `/proc` 讀取僅適用於 POSIX 或 Linux 系統。
+ 核心機制以標準函式庫實作（`socket`、`os`、`json`、`multiprocessing`、`importlib`）；第三方套件（如 `psutil`）僅作為量測之替代方案，採用時須列入相依套件清單。
+ WM 須於套件載入時檢查 Python 版本與作業系統，不符時終止並輸出原因。

**Rationale**: Python 為研究項目明定之程式語言；版本與作業系統之限制來自範例使用之語法與 Linux 專屬介面，於套件載入時檢查，可於載入其他模組前回報不相容之環境。

```python
# app/wm/main.py（於專案根目錄執行：python -m app.wm.main）
import threading
import time
from pathlib import Path

from app.wm.conf import settings
from app.wm.core import coordinator, worklist
from app.wm.core.pool import (
    CpuSampler,
    WorkerPool,
    max_workers_by_memory,
    mem_available_mb,
    should_scale_up,
)
from app.wm.core.receiver import FifoReceiver, MessageReceiver, UnixSocketReceiver


def create_receiver() -> MessageReceiver:
    path = settings.FIFO_PATH if settings.RECEIVER == "fifo" else settings.SOCKET_PATH
    Path(path).parent.mkdir(parents=True, exist_ok=True)
    if settings.RECEIVER == "fifo":
        return FifoReceiver(path)
    return UnixSocketReceiver(path)


def receive_forever(receiver: MessageReceiver) -> None:
    """原則 I → II：接收訊息並佇列為工作清單。"""
    for message in receiver.messages():
        worklist.enqueue(message)


def main() -> None:
    threading.Thread(target=receive_forever, args=(create_receiver(),), daemon=True).start()
    budget = min(settings.MEMORY_BUDGET_MB, mem_available_mb())
    limit = min(
        settings.MAX_WORKERS,
        max_workers_by_memory(budget, settings.MEMORY_RESERVE_MB, settings.PER_WORKER_MEMORY_MB),
    )
    pool, cpu = WorkerPool(), CpuSampler()
    for _ in range(min(settings.MIN_WORKERS, limit)):
        pool.spawn()
    try:
        while True:  # 原則 III、IV：指派與數量評估
            time.sleep(settings.EVALUATE_INTERVAL_SEC)
            pool.collect_reports()
            coordinator.dispatch(pool)
            if should_scale_up(
                pending=len(worklist.pending_ids()),
                idle=pool.idle_count,
                count=pool.count,
                limit=limit,
                cpu=cpu.percent(),
                cpu_limit=settings.CPU_LIMIT_PERCENT,
                since_last=time.monotonic() - pool.last_spawn,
                cooldown=settings.SCALE_COOLDOWN_SEC,
            ):
                pool.spawn()
                coordinator.dispatch(pool)
            pool.retire_idle(settings.IDLE_TIMEOUT_SEC, settings.MIN_WORKERS)
    finally:
        pool.shutdown()


if __name__ == "__main__":
    main()
```
